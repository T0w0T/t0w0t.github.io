Vocabulaire & Modèles Mentaux

Pourquoi commencer par le vocabulaire

En sécurité, les décisions sont prises sous contrainte (temps, budget, interruption). Sans un langage commun, on confond souvent : gravité technique, impact métier, risque réel, et urgence opérationnelle.

Ce qu’on veut éviter
"C’est critique" sans expliquer : critique pour qui, quand, avec quel scénario, et quelles conséquences.
Ce qu’on veut produire
Un récit testable : prérequis → exploitation → impact → mesures correctives et compensatoires.
Le bénéfice
Prioriser mieux : on corrige d’abord les chemins courts vers les impacts majeurs.

3 Éléments fondamentaux

Vulnérabilité

Une faiblesse exploitable (code, config, identité, process). Elle décrit une propriété du système.

Exemple : contrôle d’accès incomplet, dépendance vulnérable, bucket exposé.
Menace

Un acteur ou une capacité d’attaque (humain ou automatisée) qui cherche un gain.

Exemple : fraude, ransomware, concurrent, script kiddie opportuniste.
Risque

La probabilité qu’un scénario arrive et son impact.

Scénario + vraisemblance + impact + horizon de temps.
Modèle pratique : Risque = (Exposition × Exploitabilité × Motivation) × Impact
On peut réduire le risque en diminuant un des facteurs (pas uniquement en patchant).

Exposition, surface d’attaque, vecteur

Surface d’attaque

Tout ce qui est atteignable et interprété : endpoints, ports, APIs, fichiers uploadés, workers, webhooks, intégrations, consoles d’admin.

Plus elle est large, plus le coût de défense augmente.
Exposition

Une surface accessible par le mauvais public (Internet, partenaire, interne, compte non privilégié).

Une vulnérabilité non exposée peut être non prioritaire… jusqu’au pivot.
Vecteur d’attaque

Le chemin d’entrée : phishing, injection, SSRF, credential stuffing, supply chain, accès tiers.

Un vecteur “cheap” augmente la vraisemblance.
Condition d’exploitation

Pré-requis : rôle, réseau, token, timing, entropie des secrets, presence d’un service.

C’est ici que la “gravité” se nuance.

Vraisemblance vs Impact

Une même faille peut passer de “théorique” à “immédiate” si le contexte change (exposition Internet, leak de credentials, nouvel attaquant actif, nouveau chemin de pivot).

Impact faible
Inconfort, nuisance, coûts limités
Ex : fuite d’un identifiant non sensible, déni de service local, bug UI.
Impact fort
Perte financière, arrêt, données, conformité
Ex : fraude, exfiltration, ransomware, compromission d’identité.
Vraisemblance forte
Facile, automatisable, peu de prérequis
Ex : mot de passe faible, endpoint public, exploit disponible, absence de rate-limit.
Vraisemblance faible
Complexe, rare, besoin d’accès préalable
Ex : chaîne longue, timing spécifique, dépendances internes, connaissance profonde du système.
Point de pilotage : une vulnérabilité “haute” en score ne devient prioritaire que si elle ouvre un chemin court vers un impact fort, dans un contexte d’attaque plausible.

Signal, bruit, faux positifs, faux négatifs

Faux positif

Alerte déclenchée sans attaque réelle. Problème : fatigue et perte de confiance.

Remède : contexte, corrélation, seuils, enrichissement, suppression maîtrisée.
Faux négatif

Attaque réelle non détectée. Problème : découverte tardive, dégâts maximum.

Remède : couverture de logs, détection comportementale, tests de détection, purple team.
IOC
Indicateurs
IP, hash, domaine, user-agent. Rapide mais contournable.
IOA
Indicateurs d’attaque
Comportements : enchaînements, anomalies, séquences.
TTP
Tactiques / techniques
Méthodes récurrentes. Utile pour la couverture long terme.

Gouvernance : qui décide de quoi

Propriétaire du risque

La personne qui subit l’impact business et peut arbitrer (budget, délai, acceptation).

Ce n’est souvent pas l’équipe sécurité.
Mesure compensatoire

Un contrôle qui réduit le risque sans corriger la cause (ex : WAF, segmentation, monitoring renforcé).

Utile quand la correction prend du temps.
Acceptation de risque

Décision formelle : "je comprends le scénario et l’impact, et j’assume temporairement".

Elle doit avoir un horizon, des conditions, et un propriétaire.
Risque résiduel

Ce qui reste après les contrôles. Zéro risque n’existe pas : on vise un risque acceptable.

Le but : réduire les chemins faciles et rapides vers l’impact fort.
Process simple
  1. Décrire un scénario concret (pré-requis, étapes, impact).
  2. Attribuer un propriétaire de risque.
  3. Choisir : corriger / compenser / accepter.
  4. Mettre une échéance et des critères de revalidation.
  5. Mesurer : incidents, détections, exposition, dette.

Dette : technique vs sécurité

Dette technique

Le code et l’architecture rendent le changement coûteux : lenteur, bugs, retards.

Coût typique : vitesse de delivery
Dette de sécurité

Des choix augmentent l’exposition et la probabilité d’incident : versions périmées, secrets longs vécus, accès trop larges, exceptions jamais refermées.

Coût typique : incident (fraude, arrêt, exfiltration)
La dette de sécurité est une dette "à intérêts variables". Tant qu’aucun attaquant ne regarde, elle semble stable. Quand le contexte change, le taux explose.

Communication Interne

"On a une faiblesse exploitable dans tel contexte. Si un attaquant suit ce scénario, il peut produire tel impact. Voici ce qu’on fait : corriger / compenser / accepter, avec une date."

Concept Clé : La Chaîne d'Attaque

Bug vs Vulnérabilité (version exploitable)

Un bug est une divergence entre le comportement attendu et réel (qualité).
Une vulnérabilité est une divergence utile à un attaquant : elle ouvre un contournement, une lecture/écriture illégitime, ou un contrôle.

Symptôme
Crash, erreur 500, UI cassée
Peut être non exploitable.
Capacité
Lire, écrire, exécuter, usurper
Exploitable si le contexte s’y prête.

La séquence logique (chaîne standard)

1. Faiblesse Cause (code, config, identité, process)
2. Vecteur Entrée (endpoint, mail, CI/CD (Continuous Integration / Continuous Deployment), intégration, tiers)
3. Exploitation Obtention d’une capacité (lire, écrire, exécuter, contourner)
4. Expansion Escalade / pivot (droits, secrets, réseau, services)
5. Impact Objectif (fraude, exfiltration, arrêt, sabotage)
Corriger la faiblesse coupe le chemin à la racine, mais une barrière peut aussi casser le vecteur, l’exploitation, ou le pivot.

Checklist : ce qui rend une chaîne réaliste

Accès
Internet / partenaire / interne / compte basique
Inclure : exposition et segmentation.
Identité
MFA, rôle, tokens, secrets, rotation
Beaucoup d’attaques sont des attaques d’identité.
Observabilité
Logs utiles, corrélation, alerting
Sans traces, pas de détection, pas de réponse.
Frictions
Rate-limit, durcissement, sandbox, egress
Une friction peut transformer "immediate" en "coûteux".

Exemples de chaînes (par contexte)

Web (app métier)
Contrôle d’accès incomplet → accès à des objets d’un autre client → exfiltration → pression réglementaire + perte de confiance.
Ce qui accélère : endpoint public, absence de monitoring, identifiants prédictibles.
Cloud / Infra
Secret dans env / metadata → jeton d’accès → accès stockage → extraction données → mouvement latéral vers CI/CD (Continuous Integration / Continuous Deployment).
Ce qui accélère : droits trop larges, pas de rotation, logs incomplets.
Identité / AD
Mot de passe faible → accès poste → collecte tickets/credentials → élévation → compromis d’administration → ransomware.
Ce qui accélère : privilèges hérités, délégations, comptes de service.
Message clé : l’attaque n’est pas un événement, c’est une progression. Le défenseur perd rarement sur une étape "magique", il perd sur l’enchaînement.

Ce qu’il faut prouver (dans un pentest, ou un incident)

Preuve de capacité
Lecture/écriture, exécution, usurpation, contournement
Sans sur-collecter : juste assez pour être indiscutable.
Preuve d’impact
Accès données sensibles, action critique, arrêt, fraude plausible
Toujours relier à un scénario métier.
Distance à l’objectif
Nombre d’étapes restantes, prérequis manquants
La direction comprend "combien de portes restent".
Chemins alternatifs
Si on corrige A, l’attaquant passe-t-il par B ?
Utile pour prioriser la dette.

Concept Clé : Les Barrières

Idée centrale

On n’empêche pas toutes les attaques. On construit des barrières pour casser la chaîne à plusieurs endroits. Le but : rendre l’attaque coûteuse, détectable, et limitée.

Une barrière est utile si elle a : un objectif clair, une couverture connue, des métriques, et un plan de maintenance (sinon elle devient décorative).
1

Prévenir (Prevent)

Réduire l’exposition et l’exploitabilité. C’est la barrière la moins chère… avant incident.

Exemples
MFA, patching, durcissement, moindre privilège, WAF, SAST (Static Application Security Testing) /DAST (Dynamic Application Security Testing).
Mesures
taux de MFA, couverture patch, surface exposée, secrets rotés.
2

Détecter (Detect)

Savoir qu’on est attaqué maintenant. Sans détection, on découvre l’incident par les dégâts.

Exemples
SIEM, EDR, alerting, corrélation, détection IOA/TTP.
Mesures
MTTD, taux faux positifs, couverture logs, tests de détection.
3

Contenir (Contain)

Limiter la propagation et réduire l’impact maximal. On suppose que l’attaquant a un pied dedans.

Exemples
segmentation, egress control, isolation, PAM, break-glass.
Mesures
temps d’isolation, blast radius, privilèges, chemins de pivot.
4

Récupérer (Recover)

Revenir à un état sain et prouvé. La reprise sans confiance, c’est redémarrer dans l’incertitude.

Exemples
backups immuables, PRA/PCA, golden images, re-deploy.
Mesures
Tests de restauration, intégrité, délais de rotation.

Relier les barrières à la chaîne

Couper le vecteur
Prévention : réduire exposition, réduire surface, durcir.
Voir l’exploitation
Détection : logs utiles, alertes, corrélation.
Limiter le pivot
Confinement : segmentation, egress, moindre privilège.
Réduire la durée d’arrêt
Récupération : PRA, backups, reconstruction fiable.

Analyse d'un Pentest

Lecture "barrières" : où la chaîne est passée, où elle a été cassée.

Prévention
  • Faiblesse présente depuis longtemps (dette de sécurité).
  • Contrôles d’accès / secrets / durcissement insuffisants.
  • Surface d’attaque inutile (features de test, endpoints oubliés).
Détection
  • Actions longues sans alerte : manque de logs exploitables ou de corrélation.
  • Peu de signaux sur l’anomalie (IOA) : scans, erreurs, patterns d’accès.
  • Absence de tests de détection réguliers.
Contenir
  • Segmentation : certains accès latéraux bloqués.
  • Réduction du blast radius : tout n’est pas atteignable depuis un point compromis.
  • Mais : un pivot reste possible si identité/secret est compromis.
Récupération
  • Question : restauration testée ? back-ups immuables ? temps de reprise ?
  • Sans exercices, le PRA est souvent théorique.
"Investir dans des murs plus hauts ne sert à rien si personne ne regarde les caméras, et si l’intérieur n’est pas compartimenté."

Transformer un pentest en feuille de route

Un rapport utile propose des actions alignées sur les barrières : rapides, structurantes, mesurables.
Quick wins (jours)
réduire exposition, couper endpoints inutiles, durcir auth, limiter tokens, logs critiques.
Structure (semaines)
segmentation, moindre privilège, durcissement CI/CD (Continuous Integration / Continuous Deployment), rotation secrets, détection IOA.
Résilience (mois)
PRA testé, backups immuables, exercices d’incident, coverage detection, inventaire surfaces.
Notes

# Angle "direction"

"On n’achète pas de la sécurité, on achète de la réduction de risque mesurable."


# Angle "opérations"

"Une barrière non testée régulièrement doit être considérée comme absente."


>> Prévenir coûte peu, détecter coûte moyen, récupérer coûte cher.

Comprendre l'Adversaire (Kill Chain)

Objectif : penser comme l’attaquant

Une attaque réussie n’est presque jamais un “coup de génie”. C’est une progression par petites opportunités : exposition, faiblesse, identité, pivot, objectif. La Kill Chain sert à décrire cette progression pour mieux l’empêcher, la détecter, et la contenir.

1) Entrée
Recon
2) Brèche
Accès
3) Prise
Expansion
4) Gain
Impact
Astuce : chaque phase a 4 angles à documenter : objectif, méthodes (TTP), signaux, barrières.

L'attaquant est opportuniste : il cherche le chemin de moindre résistance. Si on durcit la Phase 01 et 02, il passe à une cible plus facile.

Phase 01 : Reconnaissance

Ce que l’attaquant cherche

Réduire l’incertitude. L’adversaire veut répondre à 4 questions : où attaquer, quoi exploiter, qui cibler, comment rester discret.

Livrables de la reconnaissance

  • Inventaire d’assets : domaines, sous-domaines, IP, services, SaaS, environnements de test.
  • Cartographie technique : techno, versions, chemins, endpoints, bannières.
  • Cartographie orga : emails, équipes, fournisseurs, outils internes, habitudes (phishing).
  • Repérage des “portes secondaires” : panels admin oubliés, ports non nécessaires, docs exposées.

Méthodes (TTP) détaillées

OSINT
  • LinkedIn : rôles, tech stack implicite
  • Job posts : outils, cloud, SIEM, EDR
  • Docs publics : URLs, tokens accidentels
  • Conférences / slides : schémas d’archi
Enumeration
  • DNS + subdomains
  • Scan ports / services
  • Fuzzing de chemins
  • Fingerprinting (headers, erreurs)
Fuites & exposition
  • Repos publics, historiques
  • Secrets dans CI logs
  • Buckets / storage publics
  • Paste / leaks / creds dumps
Préparation sociale
  • Modèles d’email crédibles
  • Usurpation fournisseur
  • Prétextes (factures, RH)
  • Ciblage des “rôles pivot”

Signaux de détection (ce qui se voit)

  • Pic de 404/403 sur endpoints sensibles, séquences “scanner-like”.
  • DNS queries sur sous-domaines inexistants, variations systématiques.
  • Augmentation de requêtes sur /admin, /.git, /actuator, /swagger, etc.
  • Forte entropie de paramètres (fuzzing) et erreurs corrélées.

Barrières efficaces (phase 01)

  • Réduction surface : fermer ports inutiles, enlever envs de test, couper endpoints legacy.
  • Hygiène d’exposition : pas de bannières bavardes, erreurs non verbeuses.
  • Gestion des secrets : scanners de secrets, rotation, politiques repo.
  • WAF + rate-limit : rendre le scan coûteux et visible.
  • Monitoring : dashboards scan/enum, alertes sur patterns d’exploration.
Mesure utile : “surface exposée” (nombre d’assets publics) + “temps de détection scan” (MTTD recon).
Notes

Communication

"Avant d’attaquer, l’adversaire fait ses courses. Notre job : rendre le magasin petit, surveillé, et sans produits explosifs en rayon."


>> Si la recon est simple, l’attaque sera rapide.

Erreurs fréquentes côté défense

  • Oublier des assets (shadow IT, sous-domaines temporaires).
  • Exposer des consoles admin “pour dépanner”.
  • Laisser des erreurs/headers qui révèlent stack + versions.
  • Ne pas corréler les signaux (bruit) en alertes actionnables.

Phase 02 : Accès Initial

Le vrai nerf : l’identité

Beaucoup d’attaques modernes entrent par l’authentification ou la session. Une vuln technique est utile, mais un compte valide est souvent “plus simple”.

Voies d’entrée (détaillées)

Phishing / Social
  • Vol de credentials + MFA fatigue
  • Vol de session (cookie, token)
  • OAuth consent (app malveillante)
  • Usurpation fournisseur / facture
Brute force “soft”
  • Password spraying (faible bruit)
  • Credential stuffing (lists leaks)
  • Réutilisation mots de passe
  • Reset password mal protégé
Exploitation web
  • SQLi, IDOR, SSRF, file upload
  • RCE, deserialization, template inj
  • Auth bypass, logic flaws
  • API exposures (swagger, debug)
Supply chain / Tiers
  • Intégrations SaaS trop permissives
  • Clés API partagées
  • CI/CD (Continuous Integration / Continuous Deployment) secrets + runners
  • Prestataires avec accès durable

Ce qui rend l’accès initial “probable”

  • Exposition : login accessible Internet + pas de rate-limit.
  • MFA faible : absence, SMS only, pas de device binding, pas de phishing-resistant.
  • Sessions permissives : cookies long-lived, refresh illimité, rotation absente.
  • Erreurs bavardes : révélation d’utilisateurs, d’états, de stack.
  • Gestion comptes : comptes dormants, onboarding/offboarding lent.

Signaux de détection (phase 02)

  • Auth anomalies : échecs en rafale, spray (1 essai sur N comptes), nouveaux devices.
  • Impossible travel : connexions impossibles, changements rapides de pays/ASN.
  • Token events : création d’app OAuth, refresh en boucle, sessions multiples.
  • Web exploitation : pics 500, payloads typiques, patterns d’énumération IDs.
Mesures utiles : taux MFA, temps moyen de révocation session, taux de spray détecté, couverture logs auth.
Notes

# Message

"On ne sécurise pas un système, on sécurise des identités et des sessions."


>> Plus l’accès initial est discret, plus l’impact final est violent.

Barrières efficaces (phase 02)

  • MFA phishing-resistant (FIDO2/WebAuthn) pour comptes sensibles.
  • Rate-limit + lockout intelligent + détection spray.
  • Durcir sessions : rotation, device binding, TTL raisonnable, revoke global.
  • Secure-by-default : pas de debug endpoints, pas de swagger public.
  • Secure SDLC (Software Development Life Cycle) : revues, SAST/DAST, patching dépendances.

Phase 03 : Expansion

L’objectif : augmenter le “blast radius”

À partir d’un accès initial, l’adversaire veut monter en privilèges, se déplacer et se rendre durable. C’est la phase où les secrets et les permissions font (très) mal.

Sous-objectifs (structure)

Escalade
Exploiter droits trop larges, configurations faibles, secrets récupérés.
Mouvement latéral
Aller vers les systèmes qui “valent” quelque chose (AD, DB, CI/CD (Continuous Integration / Continuous Deployment)).
Persistance
Assurer un retour : tokens, comptes, clés, tâches, backdoors discrètes.

Techniques fréquentes (TTP)

  • Secret hunting : env vars, config files, logs, vault, metadata cloud, cookies.
  • Abus IAM/AD : permissions héritées, groupes larges, délégations dangereuses.
  • Pivot réseau : proxy, tunnel, egress, accès à des services internes.
  • Living-off-the-land : outils natifs, commandes légitimes, faible bruit.
  • Persistance : clés API, refresh tokens, comptes “service”, scheduled jobs.

Signaux de détection (phase 03)

  • Accès latéraux : nouvelles connexions internes, port/proto inhabituels.
  • Changements IAM : création de clés, policies, ajout à des groupes.
  • Credential access : lectures de stores, process suspects, pics d’accès à secrets.
  • Persistences : nouvelles tâches planifiées, nouveaux comptes, tokens longs vécus.
Mesures utiles : temps d’isolement, nombre de chemins de pivot, privilèges effectifs, couverture EDR.
Notes

Communication

"L’attaquant ne gagne pas quand il entre. Il gagne quand il devient difficile à déloger."


>> Une segmentation partielle vaut mieux que rien : elle casse le pivot.

Barrières efficaces (phase 03)

  • Moindre privilège + revues régulières des droits.
  • Segmentation + egress control pour limiter les pivots.
  • Rotation secrets + vault + suppression des secrets “dans le code”.
  • PAM et “break-glass” contrôlé pour accès admin.
  • EDR + logs d’admin + audit des changements IAM/AD.

Phase 04 : Impact

Impact : ce que l’entreprise ressent

L’impact n’est pas “technique”. Il est métier : argent, arrêt, conformité, réputation, perte de confiance, coûts de remédiation.

Catégories d’impact (en clair)

  • Confidentialité : exfiltration de données (clients, RH, IP, secrets).
  • Intégrité : altération (fraude, modification de transactions, sabotage logique).
  • Disponibilité : arrêt de service, ransomware, destruction.
  • Traçabilité : effacement logs, impossibilité d’enquête.

Scénarios typiques (détaillés)

Exfiltration + extorsion
Vol de données puis menace de publication (pression).
Ransomware
Chiffrement + arrêt + négociation, souvent après phase 03 réussie.
Fraude
Changement IBAN, faux fournisseur, manipulation workflow.
Sabotage discret
Altération lente, suppression ciblée, perte de confiance “invisible”.

Signaux de détection (phase 04)

  • Exfil : volumétrie sortante, connexions vers destinations nouvelles, staging (archives).
  • Ransom : créations massives, extensions, process de chiffrement, désactivation EDR.
  • Fraude : changements d’IBAN, workflows anormaux, validations contournées.
  • Effacement : logs supprimés, audit désactivé, comptes “effaceurs”.
Mesures utiles : MTTD impact, tests de restauration, volume max exfil avant alerte.
Notes

Communication

"Le pire n’est pas d’être attaqué. Le pire est de le découvrir quand il est trop tard." "Le amendes ne tombent pas quand les données sont volées, mais quand on ne peut pas prouver que tout a été mis en oeuvre pour les protéger."


>> Une récupération non testée est une promesse non tenue.

Barrières efficaces (phase 04)

  • Backups immuables + tests réguliers.
  • IR plan : isolation rapide, communication, playbooks.
  • Segmentation pour limiter propagation ransomware.
  • DLP / egress control pour réduire exfiltration.
  • Journalisation inviolable (centralisée, rétention, alertes suppression).

L'impact est la conséquence maximale plausible d'un scénario d'attaque (et pas uniquement le "pire imaginable"). Un bon impact est :

  • Concret : décrit ce qui change pour l'entreprise (argent, arrêt, données, obligations).
  • Mesurable : volume de données, durée d'arrêt, coût, nombre de personnes touchées.
  • Lié au scénario : impact dépend des droits obtenus et des systèmes atteints.
  • Compatible pilotage : on doit pouvoir décider d'une action (corriger / compenser / accepter).

Dimensions d'impact (métier)

Confidentialité
Exfiltration ou divulgation de données sensibles (santé, identité, finance, secrets).
Intégrité
Modification non autorisée : fraude, changement de contrats, altération de transactions ou de décisions.
Disponibilité
Arrêt ou dégradation : incapacité de traiter les dossiers, remboursements, service client, partenaires.
Conformité / Preuve
Obligations réglementaires, capacité à prouver ce qui s'est passé (logs), audits, sanctions.
Réputation
Perte de confiance, difficulté à signer de nouveaux contrats, crise médiatique.
Coût de remédiation
Rebuild, forensic, reroll secrets, assistance juridique, communication, monitoring, support client.

Échelle simple (1 à 5) pour décider vite

L'objectif est d'avoir une échelle stable et répétable. Exemple générique adapté au contexte mutuelle :

  1. Faible : impact local, données non sensibles, gêne limitée.
  2. Modéré : exposition restreinte, coûts limités, peu d'utilisateurs.
  3. Sérieux : données sensibles ou service critique partiel, coût notable.
  4. Majeur : atteinte santé/identité à grande échelle ou arrêt opérationnel significatif.
  5. Critique : arrêt prolongé, exfiltration massive santé, fraude majeure, crise de confiance.
Bon réflexe : si vous hésitez entre deux niveaux, choisissez le plus bas et notez la condition qui ferait basculer au niveau supérieur (volume, durée, périmètre).

Preuves utiles (pentest) pour démontrer l'impact sans sur-exploiter

  • Confidentialité : exemple d'accès à une fiche (anonymisée), preuve de chemin, volume estimable.
  • Intégrité : preuve de modification contrôlée (champ non critique), audit trail si présent.
  • Disponibilité : preuve d'action pouvant dégrader (queue saturée, endpoint coûteux), sans provoquer d'incident réel.
  • Accès aux secrets : démontrer que des tokens/clefs ouvrent un périmètre plus large.
  • Blast radius : démontrer quelles briques deviennent atteignables après pivot.
Discipline : "preuve minimale suffisante". Montrer l'accès et le scénario, pas collecter inutilement.

Leviers pour réduire l'impact

  • Limiter le blast radius : segmentation, moindre privilège, séparation des environnements.
  • Récupération : backups immuables, tests de restauration.
  • Traçabilité : logs centralisés, rétention, alertes suppression, horodatage.
  • Protection données : chiffrement au repos et en transit, tokenisation, minimisation.
  • Process : playbooks, isolation rapide, exercice de crise (table-top).

Dossier : Probabilité

La probabilité n'est pas "la chance". C'est le coût total de l'attaque vu par l'adversaire : accès, effort, risques d'être détecté, et valeur attendue.

Structure
  • Exposition : est-ce atteignable (Internet, partenaires, interne) ?
  • Exploitabilité : est-ce facile (prérequis, complexité, maturité exploit) ?
  • Motivation : est-ce intéressant (valeur, opportunisme) ?
  • Frictions : contrôles et coûts (MFA, rate-limit, segmentation, egress) ?
  • Détectabilité : quelle probabilité d'être vu tôt ?

Échelle simple (1 à 5) pour scorer la probabilité

  1. Très faible : accès rare, prérequis élevés, peu réaliste, fort contrôle/détection.
  2. Faible : faisable mais coûteux, demande compétences spécifiques, fenêtre étroite.
  3. Moyenne : exposition partielle, certains contrôles, exploitation plausible.
  4. Élevée : accessible, exploit simple, automatisable, faible friction.
  5. Très élevée : "cheap" : internet-exposé, identités faibles, exploit public, faible détection.
Conseil : scorer en expliquant 2 ou 3 arguments max. Si vous avez besoin d'un roman, c'est que l'info manque.

Ce qui fait exploser la probabilité (signaux "danger")

  • Surface exposée Internet + endpoint sensible (admin, auth, API critique).
  • Identité fragile (MFA absent ou contournable, sessions longues, tokens réutilisables).
  • Exploit mature disponible ou attaque automatisable (spray, stuffing, vuln commune).
  • Faibles frictions (pas de rate-limit, pas de WAF, pas de détection corrélée).
  • Détection faible (logs manquants, alertes bruyantes, SOC aveugle).

Où agir pour réduire la probabilité (actions typiques)

  • Réduire l'exposition : fermer assets inutiles, restreindre IP, protéger admin.
  • Renforcer l'identité : MFA robuste, sessions, rotation/revocation tokens.
  • Ajouter de la friction : rate-limit, WAF, détection sur patterns recon/auth.
  • Casser le pivot : segmentation, egress control, moindre privilège.
  • Rendre visible : logs utiles, alerting, tests de détection.

# Message

"La probabilité baisse quand l'attaque devient chère, bruyante, et incertaine."

Dossier : Exposition

Définition

L'exposition décrit qui peut atteindre quoi. Deux systèmes identiques peuvent avoir des risques totalement différents selon leur exposition.

Axes d'exposition (pratiques)

  • Internet : tout le monde peut tenter, donc automatisation massive possible.
  • Partenaires : tiers avec accès, intégrations, webhooks, SSO.
  • Interne : exposition réduite, mais pivot possible après accès initial.
  • Identité : comptes, rôles, tokens, sessions, comptes dormants.
  • Admin : consoles, backoffice, CI/CD (Continuous Integration / Continuous Deployment), observabilité, vault.

Métriques simples (pilotables)

  • Nombre d'assets exposés (domains, sous-domaines, IP, ports, endpoints).
  • Part des surfaces critiques protégées (admin derrière VPN, allowlist, SSO fort).
  • Temps moyen de suppression d'un asset "shadow" (découverte → retrait).
  • Taux de comptes dormants et temps d'offboarding.
  • Couverture rate-limit / WAF sur endpoints sensibles.

Réduction d'exposition (actions concrètes)

  • Inventaire continu (assets, DNS, certs, cloud resources) et gouvernance "owner".
  • Fermeture des environnements de test et des interfaces admin non nécessaires.
  • Segmentation et restrictions réseau (IP allowlist, private endpoints).
  • Durcissement des chemins d'auth (MFA, device binding, protections anti-spray).
  • Standardisation : "par défaut fermé", exceptions temporaires avec échéance.

Dossier : Exploitabilité

Définition

L'exploitabilité mesure la facilité à obtenir une capacité (lire, écrire, exécuter, usurper) à partir d'un point d'entrée. Elle dépend surtout des prérequis et de la maturité de l'attaque.

Facteurs qui augmentent l'exploitabilité

  • Peu de prérequis : pas d'auth, pas d'accès interne, pas de conditions rares.
  • Complexité faible : reproduction stable, pas de timing fragile.
  • Automatisable : scripts existants, scans massifs, exploit public.
  • Privilèges obtenus : plus la capacité est forte, plus la chaîne devient courte.
  • Absence de validations : contrôle d'accès insuffisant, inputs non filtrés, logique métier fragile.

Facteurs qui réduisent l'exploitabilité

  • Auth forte + contrôle d'accès robuste (objet/tenant) à chaque action.
  • Validations côté serveur (schémas stricts), durcissement, sandboxing.
  • Rotation tokens, secrets courts vécus, permissions minimales.
  • WAF/rate-limit + détection sur patterns de payloads.
  • Patch management et suppression des versions vulnérables.

Score rapide (1 à 5) que tout le monde peut appliquer

  1. Très difficile : rare, instable, prérequis forts, compétences élevées.
  2. Difficile : faisable mais fragile, dépend de conditions, non automatisable.
  3. Moyen : reproductible, quelques prérequis, outils possibles.
  4. Facile : reproductible, peu de prérequis, automatisable partiellement.
  5. Très facile : "clic-bouton", exploit public, faible bruit, forte capacité obtenue.

Dossier : Motivation

Pourquoi la motivation compte

Deux systèmes également exposés et exploitables ne seront pas attaqués avec la même intensité. La motivation est le multiplicateur "valeur perçue" : qu'est-ce que l'attaquant gagne.

Ce qui attire (souvent) les adversaires

  • Données sensibles monétisables (santé, identité, documents).
  • Capacité d'extorsion (ransomware, menace de publication).
  • Fraude directe (paiements, modifications de bénéficiaires, workflows).
  • Accès à des tiers (partenaires, prestataires, chaîne de confiance).
  • Visibilité publique : marque, médiatisation, effet domino.

Point de pilotage

On ne contrôle pas l'intention de l'adversaire, mais on peut : réduire la valeur accessible (minimisation, segmentation) et augmenter le coût/risque (frictions, détection).

Dossier : Frictions / Contrôles

Frictions

Les frictions augmentent le coût de l'attaque et la probabilité d'échec. Elles n'éliminent pas le risque, elles transforment une attaque "cheap" en attaque "chère".

Exemples de frictions efficaces

  • Auth : MFA robuste, contrôle session, device binding.
  • Rate-limit : anti-spray, anti-stuffing, throttling intelligent.
  • WAF : blocage d'explorations et payloads évidents, challenge.
  • Segmentation : casser la phase de pivot (réseaux, services, RBAC).
  • Egress : limiter exfiltration et C2, forcer des routes visibles.
  • Secrets : rotation, scope minimal, TTL courts, vault.

Contrôle qui "existe" vs contrôle "réel"

  • Un contrôle non mesuré est souvent décoratif.
  • Un contrôle non testé (table-top, restore test, detection test) doit être considéré comme absent.
  • Un contrôle trop bruyant (trop de faux positifs) finit ignoré.

Dossier : Détectabilité

Pourquoi c'est un facteur de probabilité

Un attaquant préfère les environnements où il peut agir longtemps sans être dérangé. Une faible détectabilité augmente la probabilité qu'une attaque "tienne" jusqu'à l'objectif.

Signaux clés à surveiller

  • Recon : pics 404/403, fuzzing, enumeration IDs.
  • Auth : spray/stuffing, impossible travel, nouveaux devices, création tokens.
  • Expansion : changements de droits, accès secrets, connexions latérales, tunnels.
  • Impact : staging (archives), volumétrie sortante, suppressions logs, chiffrement massif.

Métriques utiles

  • MTTD : temps moyen avant détection.
  • Couverture logs : auth, admin, data access, changements IAM.
  • Qualité alertes : taux de faux positifs, temps de triage.
  • Tests : exercices de détection, purple team, validation playbooks.

Dossier : Risque (Pilotage)

Le risque sert à prioriser, pas à décrire une faiblesse. Un risque bien formulé est un scénario : si X arrive via Y, alors impact Z.

Traduction en décisions

Corriger
Éliminer la cause (patch, fix code, redesign). Idéal quand faisable rapidement.
Compenser
Réduire le risque autrement (WAF, segmentation, monitoring renforcé) quand la correction prend du temps.
Accepter
Décision formelle : scénario compris, propriétaire identifié, horizon défini, revalidation planifiée.

Risque résiduel

Après contrôles, il reste toujours un risque. L'objectif n'est pas "zéro", mais un risque acceptable et maîtrisé.

La bonne question n'est pas "est-ce sécurisé ?" mais "quel scénario reste possible, à quel coût, et à quel impact ?"

Contenu minimal d'une fiche risque (propre)

  • Scénario : prérequis → exploitation → impact.
  • Score : impact, probabilité, justification courte.
  • Exposition : qui peut attaquer (Internet/interne/tiers) ?
  • Contrôles existants : prévention, détection, confinement, reprise.
  • Plan : action (corriger/compense/accept), owner, échéance, métriques.

Leviers : Réduire l'Impact

Idée centrale

Réduire l'impact, c'est limiter ce qui est atteignable même si l'attaque passe (blast radius), réduire la durée d'arrêt (RTO), réduire la perte de données (RPO), et préserver la preuve (logs).

Actions typiques

  • Segmentation réseau et applicative (systèmes critiques isolés).
  • Moindre privilège (RBAC), séparation des rôles, PAM pour admin.
  • Backups immuables + tests réguliers de restauration.
  • Plans de continuité : mode dégradé, priorisation des services essentiels.
  • Journalisation inviolable : centralisation, rétention, alertes suppression.

Leviers : Réduire la Probabilité

Idée centrale

Réduire la probabilité revient à rendre l'attaque plus coûteuse, plus bruyante, et moins fiable : réduire exposition, durcir identité, ajouter frictions, et détecter plus tôt.

Actions typiques

  • Fermer surfaces inutiles, protéger admin (VPN/allowlist/SSO fort).
  • MFA robuste, sessions courtes, révocation globale rapide, rotation tokens.
  • Rate-limit, anti-spray, WAF, protections sur endpoints sensibles.
  • Hardening, patching, suppression des versions vulnérables.
  • Détection : alertes recon/auth/pivot, tests réguliers de détection.

Méthode : Évaluer un risque proprement

Méthode rapide en 6 questions

  1. Quel est le scénario ? (pré-requis → exploitation → impact)
  2. Quelle exposition ? (Internet, interne, partenaire, rôle requis)
  3. Quelle exploitabilité ? (complexité, stabilité, automatisation)
  4. Quelle motivation ? (valeur accessible, opportunisme)
  5. Quelles frictions et détections ? (MFA, rate-limit, logs, SOC)
  6. Quel impact métier ? (CIA + conformité + réputation + coûts)

Format "fiche" recommandée (copiable)

Risque : …
Scénario : prérequis → étape → étape → impact
Impact : 1-5 (justification en 2 lignes)
Probabilité : 1-5 (exposition + exploitabilité + frictions)
Contrôles : prévention / détection / confinement / reprise
Décision : corriger / compenser / accepter
Owner + échéance : …
Mesures : …

Règles d'or

  • La justification doit tenir en quelques lignes : sinon, l'info manque.
  • Les scores doivent être cohérents entre équipes (échelle stable).
  • On priorise d'abord les chemins courts vers les impacts forts (pas les scores "bruts").
  • Un contrôle non testé est un contrôle incertain.

Impact : Confidentialité (Données Santé)

Pourquoi c'est critique en mutuelle

  • Données de santé : sensibles, fortement régulées, forte valeur d'extorsion.
  • Obligations : notification de violation, preuve, gestion de crise.
  • Conséquences : sanctions, perte de confiance, coûts support et juridiques.
Point clé : une fuite "petite" mais prouvée peut déclencher des obligations importantes.

Réduction d'impact spécifique

  • Minimisation : ne pas exposer plus que nécessaire, segmentation par périmètre.
  • Contrôle d'accès objet/tenant strict, audits d'accès aux dossiers.
  • Chiffrement et gestion de clés robuste, rotation, scopes minimaux.
  • Détection : accès massifs, exports, staging, comportements atypiques.

Impact : Disponibilité (Opérations)

Formes de perte de disponibilité

  • Arrêt total : services indisponibles (ransomware, sabotage, incident infra).
  • Dégradation : latence, files saturées, dépendances externes en panne.
  • Blocage métier : systèmes critiques indisponibles (remboursements, gestion dossiers).

Réduction d'impact (dispo)

  • PRA/PCA testés, exercices réguliers.
  • Backups immuables + procédures de restauration éprouvées.
  • Segmentation et limitations de propagation (anti-ransomware).
  • Mode dégradé et priorisation des services essentiels.

Impact : Intégrité (Fraude)

Pourquoi l'intégrité est sous-estimée

Une fraude peut durer longtemps si elle est discrète. Elle n'arrête pas les systèmes, donc elle est souvent détectée tard. En mutuelle, toute altération de données de contrats, bénéficiaires ou paiements peut avoir des effets cumulés.

Exemples de scénarios

  • Modification d'IBAN / bénéficiaire / référentiel fournisseur.
  • Altération de contrats : garanties, dates, franchises.
  • Manipulation workflow : validations contournées, double dépense.
  • Falsification de justificatifs ou d'historiques.

Réduction d'impact (intégrité)

  • Traçabilité forte : audit trail, immutabilité logique, alertes sur changements sensibles.
  • Séparation des tâches : approbations, double contrôle, seuils.
  • Détection anomalies : patterns de changements, montants, comptes, horaires.
  • Contrôle d'accès fin : objet/tenant, rôles limités, revues périodiques.

Impact : Conformité & Juridique

Pourquoi ça pèse lourd

  • Obligations liées aux données personnelles (ex : notification de violation, tenue de registres).
  • Capacité à prouver : logs, horodatage, chaîne de conservation, investigations.
  • Audits et demandes : temps, coût, mobilisation interne, risque d'amendes.
Note : dans l'UE, le régime de sanctions du RGPD peut aller jusqu'à 20 M€ ou 4% du CA annuel mondial (selon le montant le plus élevé).

Levier principal : preuve et gouvernance

  • Logs centralisés et rétention, alertes suppression, accès admin tracés.
  • Cartographie données : où sont les données sensibles, qui y accède, pourquoi.
  • Process incident : rôles, communication, décisions documentées.

Impact : Réputation & Confiance

Pourquoi c'est durable

  • La confiance se perd vite et se reconstruit lentement.
  • Les clients retiennent "fuite de données santé" plus que la cause technique.
  • Effets secondaires : hausse support, difficulté commerciale, tension partenaires.

Réduction

  • Réduire exposition et volumes (minimisation) diminue l'ampleur d'un incident.
  • Détection tôt + réponse structurée réduit la durée médiatique.
  • Preuve et transparence maîtrisée : communication factuelle, cohérente.

Impact : Coûts de Remédiation

Ce qui coûte (souvent) le plus

  • Forensic et investigation (temps, expertise, outils).
  • Reroll secrets : tokens, mots de passe, clés, certificats, accès tiers.
  • Rebuild : re-déploiement, durcissement, validation, tests.
  • Juridique : notification, accompagnement, obligations.
  • Support : hotline, gestion clients, monitoring post-incident.

Réduction

  • Inventaire secrets et rotation régulière (réduit la panique du reroll).
  • Infrastructure as code + images gold (rebuild plus rapide).
  • Playbooks et rôles clairs (réduit le chaos opérationnel).

Défense en Profondeur

La défense en profondeur n’est pas “mettre plus d’outils”. C’est multiplier les obstacles et réduire le blast radius : si une couche tombe, la suivante doit encore tenir, et la détection doit permettre de réagir vite. Cliquez sur une couche pour ouvrir le dossier complet.

1. Socle (Inventaire & Gouvernance)

On ne protège pas ce qu’on ne voit pas. Cartographie des actifs, owners, criticité, flux, dette, règles.

2. Identité (IAM & Privilèges)

MFA robuste, sessions contrôlées, moindre privilège, PAM pour admins, revues d’accès, secrets courts vécus.

3. AppSec & Infra

Secure by Design, validation serveur, durcissement, patching, WAF blocking, sauvegardes, segmentation.

4. Détection (SOC & Réponse)

Voir l’attaque pendant qu’elle arrive : logs utiles, corrélation, alertes, playbooks, isolation rapide.

Une défense “bonne” se mesure : temps de détection, temps d’isolement, nombre de chemins de pivot, capacité de restauration. Sans métriques, on confond sensation et sécurité.

Socle : Inventaire & Gouvernance

Pourquoi c’est le socle

Sans inventaire, une organisation défend des “fantômes” et oublie des “portes”. L’attaquant, lui, trouve les assets oubliés : sous-domaines temporaires, environnements de test, consoles admin, buckets, endpoints.

Contenu minimal d’un inventaire utilisable

  • Asset : nom, type (app, API, DB, VM, cluster, SaaS), environnement.
  • Owner : responsable technique et responsable métier.
  • Criticité : impact métier si indisponible / compromis.
  • Données : nature (santé, identité), volumes, sensibilité.
  • Exposition : internet / interne / partenaire, ports, auth.
  • Dépendances : SSO, CI/CD (Continuous Integration / Continuous Deployment), cloud, prestataires.
  • Contrôles : patching, WAF, logs, backups, EDR, RBAC.
Objectif : pouvoir répondre vite à “qu’est-ce qui est exposé ?”, “qui décide ?”, “quels logs existent ?”.

Gouvernance (sans bureaucratie)

  • Owners obligatoires : pas d’asset sans propriétaire.
  • Règles d’exposition : “par défaut fermé”, exceptions temporaires avec échéance.
  • Revue périodique : assets exposés, comptes dormants, droits critiques.
  • Gestion dette : versions, patching, dérogations, acceptations de risque.
  • Change management : toute ouverture réseau / admin doit être tracée.

Métriques pilotables

  • Nombre d’assets exposés Internet + évolution.
  • Temps moyen de retrait d’un asset non conforme.
  • % d’assets avec owner + criticité + données renseignés.
  • Couverture patching SLA (Service Level Agreement. Engagement de niveau de service) par criticité.
  • Couverture logs et rétention par périmètre critique.

Couche 1 : Infra & Réseau

But de la couche

Réduire l’exposition technique et casser les chemins “courts” : services inutiles, versions vulnérables, accès directs, mouvements latéraux faciles. C’est la couche qui doit rendre la recon et l’accès initial plus coûteux.

Contrôles essentiels

  • Patching / vuln management : SLA par criticité, automatisation, exemptions tracées.
  • Hardening : config sécurisée (CIS), services minimaux, ports fermés.
  • Segmentation : zones, règles est-ouest, microseg, “deny by default”.
  • WAF / reverse proxy : protections, rate-limit, règles adaptées à l’app.
  • Egress control : limiter sorties (exfiltration, C2), proxy obligatoire.
  • Secrets & config : pas de secrets en clair, rotation, scopes minimaux.

Erreurs fréquentes

  • WAF “monitor only” éternel, jamais en blocking, règles non adaptées.
  • Segmentation “sur le papier”, mais ouvertures permanentes “pour dépanner”.
  • Patching sans SLA : tout est “prioritaire”, donc rien ne l’est.
  • Admins accessibles depuis Internet (RDP/SSH/console), ou via MFA faible.
  • Absence de contrôle sortant : exfiltration facile, C2 non détecté.

Métriques utiles

  • Temps médian de patch par criticité, taux de patching dans le SLA.
  • Nombre de ports/services exposés par application.
  • Nombre de chemins de pivot possibles (connectivité est-ouest).
  • Taux de blocage WAF utile vs bruit, temps de tuning.
  • Couverture egress : % des flux sortants connus et justifiés.

Couche 2 : IAM & Privilèges

Règle du jeu moderne

Beaucoup d’attaques entrent par l’identité (comptes, sessions, tokens). IAM est la couche qui doit empêcher les accès non autorisés et limiter ce qu’un accès “volé” peut faire.

Contrôles clés

  • MFA robuste : idéalement phishing-resistant (FIDO2/WebAuthn) pour admins.
  • Moindre privilège : droits minimaux, rôles clairs, pas d’héritages “grands”.
  • PAM : comptes admin protégés, élévation temporaire, sessions tracées.
  • Gestion sessions : rotation, TTL raisonnables, révocation globale rapide.
  • Revues d’accès : trimestrielles sur périmètres critiques, offboarding strict.
  • Secrets : tokens courts vécus, scopes minimaux, rotation automatique.

Angles d’attaque typiques

  • Credential stuffing / password spraying (faible bruit).
  • Vol de session (cookies, refresh tokens), absence de device binding.
  • Comptes dormants, comptes partagés, secrets non rotés.
  • Droits trop larges : “admin de fait” via groupes.
  • Absence d’audit sur changements IAM (création clés, policies).

Métriques pilotables

  • % MFA par population (utilisateurs, admins, prestataires).
  • Temps moyen de révocation d’une session compromise.
  • Nombre de privilèges “haut” et revues réalisées dans les temps.
  • Taux de comptes dormants supprimés / désactivés.
  • Qualité logs IAM : création de clés, ajout groupes, élévations.

Couche 3 : App Security (Code & Validation)

But de la couche

Empêcher la transformation d’une faiblesse en capacité : contrôle d’accès robuste, validations serveur, séparation des tenants, sécurité par défaut. C’est la couche qui doit empêcher l’IDOR, la logique métier fragile, les injections et les bypass.

Contrôles applicatifs essentiels

  • Autorisation partout : vérification objet/tenant à chaque action.
  • Validation serveur : schémas stricts, refus par défaut, pas de confiance client.
  • Gestion erreurs : pas de fuite d’info (stack, versions, IDs).
  • Sécurité des sessions : cookies sécurisés, CSRF si nécessaire, rotation.
  • Secrets : pas dans le code, vault, scopes minimaux, rotation.
  • SDLC (Software Development Life Cycle) : revues, SAST/DAST, dépendances, SBOM (Software Bill of Materials), patching libs.

Contrôles infra applicatifs (pratiques)

  • WAF tuning (blocking) + règles sur endpoints sensibles (auth, admin, export).
  • Rate-limit sur endpoints critiques (login, search, export).
  • Headers de sécurité, CSP adaptée, durcissement.
  • Isolation des environnements : dev/test jamais “comme prod” accessible.

Métriques utiles

  • Temps de correction des vulnérabilités par criticité (SLA).
  • Couverture des contrôles d’accès (tests automatisés, revues).
  • Taux de dépendances obsolètes et temps de mise à jour.
  • Qualité des validations : bugs de logique, IDOR détectés avant prod.

Données

Pourquoi tout converge ici

Les données sont souvent l’objectif final : santé, identité, contrats, paiements, secrets. Toute défense en profondeur doit répondre à deux questions : qui peut accéder à quoi, et comment limiter l’impact si l’accès est obtenu.

Contrôles de protection des données

  • Classification : savoir quelles données sont sensibles (santé, identité).
  • Minimisation : ne collecter / conserver que le nécessaire.
  • Chiffrement : au repos + transit, gestion de clés et rotation.
  • Contrôle d’accès : objet/tenant strict, moindre privilège.
  • Traçabilité : audit d’accès, alertes sur exports et accès massifs.
  • Rétention : politiques de suppression, purge, conformité.

Signaux d’exfiltration (à détecter)

  • Exports inhabituels, requêtes massives, accès “scraping-like”.
  • Création d’archives, staging, pics réseau sortants.
  • Accès à des données hors périmètre habituel (rôles, horaires, volume).
  • Désactivation logs ou évasion de la traçabilité.

Couche 4 : Détection (SOC & Réponse)

But de la couche

Reconnaître les phases de la kill chain pendant qu’elles se produisent : recon, accès initial, expansion, impact. Une détection tardive transforme un incident en catastrophe coûteuse.

Ce qu’il faut absolument collecter

  • Auth/IAM : succès/échecs, MFA, tokens, changements de droits.
  • App : accès endpoints sensibles, erreurs, exports, actions admin.
  • Infra : EDR, process, connexions, logs système, admin sessions.
  • Réseau : flux sortants, DNS, proxy, egress, volumes.

Détection “utile” : règles & corrélations

  • Recon : burst 404/403 + patterns de fuzzing + user-agent scanner.
  • Auth : spray/stuffing + impossible travel + nouveaux devices.
  • Expansion : accès secrets + changements IAM + connexions latérales.
  • Impact : staging (zip) + volumétrie sortante + suppressions logs.
Bon réflexe : moins d’alertes, mais des alertes actionnables, avec owner et playbook.

Métriques SOC

  • MTTD : temps moyen de détection.
  • MTTR : temps moyen de réponse / containment.
  • Taux de faux positifs : bruit vs signal.
  • Couverture : % périmètre critique réellement loggé.
  • Tests : exercices, purple team, validation playbooks.

Industrialiser la Remédiation et Garanties de non-régression

Corriger une faille une fois, c’est bien. Corriger à l’échelle, c’est un process : détecter, prioriser, corriger, vérifier, empêcher la régression. Cliquez sur une carte pour ouvrir le dossier complet (rôles, SLA, templates, KPIs, pièges classiques).

Modules pratiques

Des morceaux concrets à activer : scoring, templates, ownership, et "definition of done" sécurité.

Dossier : Sécurité dans le SDLC (Software Development Life Cycle)

But

Déplacer la sécurité “à gauche” : plus on détecte tôt, moins ça coûte. L’objectif n’est pas de ralentir, mais de rendre la qualité sécurité automatique.

Minimum viable SDLC (Software Development Life Cycle) (sans usine à gaz)

  • Design : mini threat-model (actifs, flux, trust boundaries, abuse cases).
  • Dev : checklists, code review ciblée (auth, accès, inputs, secrets).
  • CI : SAST + secrets scan + dependency scan + tests de sécurité.
  • Pré-prod : DAST/IAST (Interactive Application Security Testing) sur routes critiques + config review.
  • Prod : monitoring, alerting, patching cadence, rollback maîtrisé.

Patterns “à sécuriser en priorité”

  • Authentification, gestion sessions, reset password.
  • Autorisation (RBAC/ABAC), multi-tenant, IDOR.
  • Import/export, upload, parsing, PDF/CSV, webhooks.
  • Endpoints admin, features debug, flags, environnements test.
  • Secrets : variables d’env, CI logs, config files, tokens longs vécus.

Definition of Done (sécurité)

  • Pas de secrets en clair, rotation possible, scopes minimaux.
  • Contrôles d’accès testés (cas négatifs) sur actions sensibles.
  • Inputs validés côté serveur, erreurs non verbeuses.
  • Logs utiles : auth, admin, exports, changements de droits.
  • Critiques bloquants : correction ou mitigation approuvée.

Dossier : Gestion des Vulnérabilités

But

Transformer une liste de findings en exécution : triage clair, owners, échéances, preuves, re-test. Une vuln non assignée est une vuln non corrigée.

Chaîne opérationnelle (simple)

  1. Intake : finding créé, unique, contextualisé (asset, env, owner).
  2. Triage : validation + scénario + risque (impact/probabilité).
  3. Assign : owner technique + sponsor produit si nécessaire.
  4. Plan : correctif ou mitigation + deadline + dépendances.
  5. Fix : PR/patch + tests + release.
  6. Verify : re-test + preuve de fermeture.
  7. Prevent : ajouter test/contrôle pour éviter la régression.

SLA (exemple pro)

Critique : correction ou mitigation ≤ 7 jours
Haute : correction ≤ 30 jours
Moyenne : correction ≤ 90 jours
Basse : correction à la prochaine fenêtre (ou backlog)
Règle : si le SLA ne peut pas être tenu, il faut une mitigation + une exception formelle (owner + fin).

Pièges classiques

  • Tout est “critique”, donc le triage ne sert plus à rien.
  • Pas d’owner : la vuln se balade de board en board.
  • On ferme “sur papier” sans preuve de correction (pas de re-test).
  • On corrige sans empêcher la régression (pas de test, pas de gate).
  • On ne contextualise pas : un CVSS seul ne donne pas le risque métier.

Dossier : Exceptions (Dérogations)

Définition

Une exception est une décision formelle de ne pas corriger immédiatement un risque. Elle doit être bornée dans le temps et compensée.

Champs obligatoires (sinon ce n’est pas une exception)

  • Owner : responsable qui accepte et porte la décision.
  • Scope : quel asset, quelle vuln, quels environnements.
  • Justification : pourquoi on ne corrige pas maintenant (dépendances, contraintes).
  • Mesure compensatoire : WAF, segmentation, monitoring, restriction accès, etc.
  • Date de fin : échéance, pas “indéfinie”.
  • Revalidation : revue périodique, conditions de sortie.

Exemples de compensations acceptables

  • Restreindre exposition (allowlist, VPN, suppression endpoint public).
  • Ajouter friction (rate-limit, WAF blocking, protection auth).
  • Segmenter (bloquer pivot vers données sensibles).
  • Surveiller (alertes spécifiques, dashboards, tests réguliers).
  • Réduire impact (backups immuables, durcir secrets, réduire privilèges).

Ce qu’il faut éviter

  • Exceptions sans date de fin (deviennent un “nouvel état normal”).
  • Exceptions sans mitigation (c’est un abandon, pas une dérogation).
  • Owner flou (“l’équipe”) au lieu d’une personne ou rôle responsable.
  • Pas de revalidation : le contexte change, le risque augmente, personne ne regarde.

Dossier : Security Gates CI/CD (Continuous Integration / Continuous Deployment)

Principe

Un gate est un point de contrôle automatisé qui empêche une régression sécurité. L’objectif : bloquer le critique automatiquement, et traiter le reste par triage.

Gates typiques (pragmatiques)

  • Secrets scan : tout secret détecté = build fail.
  • Dependency scan : CVE critique exploitable = build fail.
  • SAST : bloquer uniquement certaines catégories (auth, injection, RCE) selon sévérité.
  • IaC scan : ressources exposées / policy violations = fail ou warn selon criticité.
  • DAST (pré-prod) : blocage si vuln critique sur routes sensibles.

Politique recommandée (éviter le chaos)

  • Commencer en mode “warn” pour calibrer, puis passer en “block” sur le critique.
  • Garder des exceptions strictes (owner + durée + justification), jamais permanentes.
  • Limiter les faux positifs (sinon les équipes contournent le gate).
  • Relier chaque finding à un ticket/owner automatiquement.

Métriques

  • Taux de builds bloqués par criticité (et tendance).
  • Temps moyen de résolution après blocage.
  • Taux de faux positifs par outil.
  • Nombre d’exceptions actives et âge moyen.

Module : Triage & Priorisation

But

Décider vite : qu’est-ce qui bloque, qu’est-ce qui se corrige, qu’est-ce qui se compense. Un triage efficace repose sur l’équation du risque : impact et probabilité.

Checklist triage (pratique)

  • Exposition : internet, interne, partenaire ?
  • Exploitabilité : prérequis, stabilité, exploit public ?
  • Capacité : lecture/écriture/RCE ? accès admin ?
  • Blast radius : données sensibles, pivot possible ?
  • Contrôles existants : WAF, MFA, segmentation, logs ?
  • Décision : corriger, compenser, exception.

Module : Ownership & RACI

Pourquoi c’est critique

Sans owner clair, la remédiation devient une chaîne d’emails. L’industrialisation, c’est attribuer chaque risque à un système et un propriétaire.

RACI minimal (exemple)

  • Responsible : équipe qui corrige (dev/ops).
  • Accountable : owner du produit/service (décide et arbitre).
  • Consulted : sécurité (triage, guidance, re-test).
  • Informed : management, métier, conformité selon impact.

Module : Vérification & Re-test

Pourquoi re-tester

  • Une correction peut être partielle (contournable).
  • Une mitigation peut réduire le risque sans le supprimer : il faut le prouver.
  • La requalification garantit qu’on ne ferme pas “sur papier”.

Preuves attendues

  • Commit/PR + description du correctif.
  • Test ajouté (unit/integration) qui échoue avant et passe après.
  • Re-test (DAST ou validation manuelle) avec capture de preuve.
  • Contrôle de régression : gate ou règle CI.

Module : KPIs de Remédiation (Pilotage)

Ce qu’on veut piloter

Les KPIs doivent mesurer la capacité à réduire le risque dans le temps, pas “le nombre de tickets”. On veut voir : vitesse, discipline, et réduction de surface.

KPIs utiles (et actionnables)

  • MTTR vuln : temps moyen de correction par criticité.
  • % dans SLA : respect des délais par criticité.
  • Backlog : volume et âge des vuln (médiane + percentiles).
  • Exceptions actives : nombre + âge + date de fin.
  • Régressions : vuln similaires réintroduites (signal SDLC (Software Development Life Cycle) faible).
  • Surface exposée : nombre d’assets/endpoints publics critiques.

Pièges de pilotage

  • Optimiser le KPI au lieu de réduire le risque (fermetures “papier”).
  • Comparer des équipes sans contextualiser (périmètre, exposition, dette).
  • Ne pas suivre les exceptions (deviennent permanentes).
  • Ignorer les régressions (absence de tests/gates).

Qui fait quoi ? (RACI)

Un RACI sert à éviter les phrases toxiques du genre “c’était pas chez nous”. Il fixe les responsabilités, les décisions, et les escalades. Cliquez sur une action ou un rôle pour ouvrir le dossier (définition, livrables, preuves, pièges, exemple concret).

RACI : Définition (R / A / C / I)

RACI découpe une responsabilité en 4 rôles. L’objectif : savoir qui agit, qui décide, qui est consulté, et qui doit être informé. Sans ça, les projets ralentissent et les risques restent “entre deux chaises”.

R = Responsible (Réalise)
Exécute le travail. Il peut y avoir plusieurs R, mais ils doivent être clairement délimités.
A = Accountable (Redevable / Décide)
Porte la responsabilité finale et arbitre. En pratique, il doit y avoir un seul A par action.
C = Consulted (Consulté)
Donne un avis avant décision/exécution (expertise, conformité). Le C influence, mais ne bloque pas par défaut.
I = Informed (Informé)
Reçoit l’information. Pas de validation attendue. L’I est important pour la traçabilité et la confiance.
Règle pratique : si tout le monde est “C”, personne ne décide. Si tout le monde est “A”, personne n’assume.

Principes de Gouvernance (qui fait quoi, vraiment)

Principe 1 : La sécurité cadre et contrôle

  • Définit les politiques (SLA, gates CI/CD (Continuous Integration / Continuous Deployment), standards, exceptions).
  • Priorise via le risque (impact/probabilité), pas juste via un score brut.
  • Audite : mesure l’application et vérifie la fermeture des points critiques.
  • Peut exercer un veto sur certains scénarios (ex : risque critique non compensé).

Principe 2 : La DSI opère et rend possible

  • Fournit les plateformes (IAM, logging, patching, backup, WAF, EDR).
  • Applique le hardening et la segmentation (réduit l’exposition structurelle).
  • Industrialise les runbooks (PRA, incident response, rotation secrets).

Principe 3 : L’App Owner corrige sur son périmètre

  • Maintient l’inventaire de son application (données, flux, dépendances).
  • Fixe le code et corrige la logique métier (autorisation, validations, tests).
  • Accepte la discipline des gates CI/CD (Continuous Integration / Continuous Deployment) (empêche la régression).

Principe 4 : Le Métier décide du risque résiduel

  • Arbitre entre coût de réduction et exposition acceptée.
  • Signe les exceptions et finance les mesures lourdes quand nécessaire.
  • Porte la responsabilité de l’impact (clients, opérations, réputation).
Le Métier n’a pas besoin de “connaître la technique”, mais doit comprendre le scénario et l’impact.

Escalade & Arbitrage

L’escalade doit être prédictible : qui tranche, quand, et avec quelles informations. Sans mécanisme, les “critique” traînent et se transforment en incident.

Triggers d’escalade (exemples)

  • SLA dépassé sur une vuln critique ou haute sans mitigation.
  • Risque critique sur asset exposé Internet (sans contrôle compensatoire solide).
  • Exception demandée sans date de fin ou sans owner identifié.
  • Blocage CI/CD (Continuous Integration / Continuous Deployment) contourné (policy violation).
  • Incident détecté : activation du mode crise et arbitrage business.

Format d’arbitrage (1 page)

  • Scénario (pré-requis → exploitation → impact).
  • Score risque (impact/probabilité) + justification courte.
  • Options : corriger / compenser / accepter.
  • Coût et délai de chaque option.
  • Décision (A) + date + owner + revalidation.

Rôle : RSSI / Sécurité

Mission
Définir le cadre (politiques, SLA, contrôles), piloter le risque et vérifier l’application. La sécurité n’est pas l’équipe qui “fait tout”, c’est l’équipe qui rend l’exécution fiable.
Livrables attendus
  • Politiques : SLA, gates CI/CD (Continuous Integration / Continuous Deployment), exceptions.
  • Triage : priorisation par risque.
  • Audits et re-tests sur critique.
  • Tableaux de bord : MTTD/MTTR, backlog, exceptions actives.
Pièges
  • Se substituer à l’exécution (dev/ops) au lieu de la structurer.
  • Définir des règles impossibles (contournements assurés).

Rôle : DSI / Ops

Mission
Opérer l’infra et fournir les plateformes de sécurité : IAM, logs, patching, backup, WAF, segmentation, runbooks incident/PRA.
Livrables
  • Patching dans le SLA, hardening standardisé.
  • Collecte logs fiable + rétention.
  • Backups immuables + tests de restauration.
  • Isolation/containment en cas d’incident.

Rôle : App Owner

Mission
Posséder l’application : inventaire, dépendances, données, correction du code, et conformité aux gates CI/CD (Continuous Integration / Continuous Deployment). Si l’app est vulnérable, c’est l’owner qui orchestre la correction.
Livrables
  • Fix code + tests de non-régression.
  • Preuves de correction + re-test.
  • Documentation des flux et données sensibles.

Rôle : Métier

Mission
Arbitrer entre risque et coût. Le Métier est accountable quand l’impact touche les clients, l’opérationnel, l’argent, la réputation. Il signe les acceptations de risque.
Livrables
  • Décision documentée (acceptation, budget, priorités).
  • Date de fin et revalidation des exceptions.
  • Participation aux exercices de crise (table-top).

Action : Inventaire Applicatif

But

Savoir ce qui existe, qui décide, et où sont les données. Sans inventaire, la sécurité travaille “au radar” et l’organisation oublie des surfaces d’attaque.

Livrables (preuves)

  • Fiche appli : owner, criticité, données, dépendances.
  • Exposition : domaines, endpoints, interfaces admin.
  • Contrôles : MFA, WAF, logs, backup, patching SLA.
  • Revue périodique : assets “shadow” supprimés.

Pièges

  • Inventaire “Excel” sans owner et sans mise à jour.
  • Pas de règle “no owner, no prod”.
  • Pas d’inventaire des sous-domaines / environnements de test.

Action : Correction de Vulnérabilité

But

Corriger vite ce qui réduit le risque. Différencier clairement : patch infra vs fix code, et exiger un re-test.

Definition of Done

  • Correctif livré (PR/patch) + tests / validation.
  • Re-test (automatique ou manuel) prouvant la fermeture.
  • Contrôle anti-régression (gate CI/CD (Continuous Integration / Continuous Deployment), règle, test ajouté).
  • Communication : statut et impact résiduel si mitigation.

Pièges

  • Fermer “ticket” sans preuve.
  • Correction partielle contournable.
  • Mitigation sans suivi (devient permanente).

Action : Acceptation de Risque

But

Décision formelle : “je comprends le scénario, l’impact, et je choisis de ne pas réduire le risque maintenant”. Ce n’est pas une excuse, c’est un acte de gouvernance.

Champs obligatoires

  • Scénario (pré-requis → exploitation → impact).
  • Score (impact/probabilité) + justification courte.
  • Mesures compensatoires (si besoin).
  • Date de fin et revalidation.
  • Signature du Métier (Accountable).
Point clé : l’acceptation transfère la responsabilité de la décision sur le Métier. La sécurité peut exercer un veto si le risque dépasse le seuil défini (ex : critique exposé Internet sans compensation).

Action : Gestion des Tiers

But

Un prestataire peut devenir un chemin d’accès. La gestion des tiers vise à contrôler : accès, données, obligations, et capacité de réponse (en cas d’incident).

Contrôles essentiels

  • Due diligence : exigences sécurité, audits, questionnaires, preuves.
  • Accès : moindre privilège, comptes nominatifs, MFA, rotation.
  • Données : minimisation, chiffrement, clauses, localisation.
  • Incident : notification, délais, responsabilités, tests.

Pièges

  • Comptes partagés “prestataire”, sans expiration.
  • Accès VPN large, pas segmenté.
  • Contrat sans clauses incident et sans exigences de preuve.

Action : IAM / Comptes & Accès

Ce que “bien gouverner” veut dire

  • Règles d’accès : MFA, PAM, revues périodiques, offboarding.
  • Traçabilité : changements de rôles, accès admin, tokens.
  • Opérations : création/suppression, process d’urgence, audits.

Preuves attendues

  • Rapports MFA et exceptions.
  • Liste privilèges élevés et revues signées.
  • Journal d’audit des changements IAM.

Action : Logs & Détection (SOC)

Objectif

Détecter l’attaque pendant qu’elle se déroule. Pour ça, il faut des logs utiles, corrélés, et actionnables.

Preuves

  • Couverture logs sur auth, admin, exports, changements IAM.
  • MTTD/MTTR mesurés, playbooks testés.
  • Alertes “signal” (peu, mais fiables).

Action : Backups & PRA

Objectif

Garantir la reprise : backups immuables, procédures de restauration, tests réguliers.

Preuves

  • Rapport de tests de restauration (dates, résultats, temps).
  • Backups immuables, rétention, séparation des accès.
  • Runbooks validés (qui fait quoi en crise).

Action : Gestion Incident & Crise

Objectif

Contenir vite, préserver la preuve, décider business, et restaurer. La gouvernance de crise est un RACI en accéléré.

Preuves attendues

  • Playbooks et exercices (table-top) réalisés.
  • MTTD/MTTR mesurés, décisions tracées.
  • Capacité d’isolement et de rollback testée.

Tableau de Bord & KPIs

Un tableau de bord sert à décider. Les KPIs doivent montrer : où est le risque, si on progresse, et qui doit arbitrer.

Décisions à prendre ce mois

Règles de design d’un bon KPI

Le KPI doit être actionnable

  • Définition claire : on sait exactement ce qui est compté (et ce qui ne l’est pas).
  • Source de vérité : un système (scanner, ticketing, IAM, SIEM), pas “à la main”.
  • Seuils : vert/orange/rouge, connus à l’avance.
  • Owner : quelqu’un est accountable quand ça passe au rouge.
  • Plan : actions standard, escalade, date de revalidation.

Pièges classiques

  • Optimiser le chiffre au lieu de réduire le risque (fermetures “papier”).
  • Mélanger des périmètres (prod vs dev, internet vs interne) et tirer de mauvaises conclusions.
  • Ne pas suivre les exceptions (elles deviennent un nouveau standard).
  • KPIs “vanity” : beaucoup de volume, zéro décision.
Règle pratique : “Si ce KPI devient rouge demain, qui fait quoi dans les 48h ?” Si personne ne sait, il manque un maillon.

KPI : Failles Critiques

Ce que ça mesure

Le nombre de vulnérabilités critiques ouvertes sur le périmètre défini. L’intérêt n’est pas le nombre en soi, mais la capacité à empêcher qu’il augmente et à le ramener à zéro.

Définition (à figer)

  • Critique = exploitable + impact élevé + exposition significative (ex : internet / pivot vers données sensibles).
  • Inclure seulement : prod (ou prod + préprod si identique), assets inventoriés.
  • Exclure : faux positifs validés, findings compensés avec exception active (à condition de les compter ailleurs).

Seuils & actions

  • Rouge : ≥ 1 critique exploitable sur asset exposé internet sans compensation.
  • Action standard : assign owner + mitigation immédiate + plan de fix + re-test.
  • Escalade : si SLA dépassé ou si aucune mitigation possible.

Pièges

  • Compter “tout” en critique (perte totale de priorisation).
  • Fermer sans preuve (pas de re-test).
  • Masquer via exceptions sans date de fin (bombe à retardement).

KPI : MTTR (Temps de correction)

Ce que ça mesure

Le délai moyen entre détection/validation et fermeture vérifiée. Attention : “fermer un ticket” n’est pas “corriger”.

Formule (exemple)

  • MTTR = moyenne (date_clôture_vérifiée - date_triage_validé).
  • Segmenter par criticité (critique/haute/moyenne) et par périmètre (prod vs non-prod).
  • Regarder aussi la médiane et les percentiles (p50/p90) : la moyenne seule cache les extrêmes.

Actions pour améliorer

  • Ownership clair et auto-assignment.
  • Gates CI/CD (Continuous Integration / Continuous Deployment) sur le critique (empêcher la régression).
  • Réduction des faux positifs (sinon le triage sature).
  • Runbooks de fix (patching, config, hotfix) et fenêtres de déploiement prévisibles.

KPI : Exceptions actives

Ce que ça mesure

Le nombre d’exceptions (dérogations) en cours. C’est une mesure de la dette de risque officiellement acceptée.

Ce qu’on veut voir

  • Une tendance stable ou décroissante.
  • 0 exception expirée (sinon, gouvernance cassée).
  • Chaque exception liée à une vuln/risque, un owner, une date de fin, et une compensation.
Une exception expirée n’est pas “un retard”, c’est une décision non revalidée. À traiter comme un incident de gouvernance.

KPI : Couverture MFA

Ce que ça mesure

La proportion de comptes soumis à une authentification multi-facteurs sur un périmètre défini. L’important : quels comptes (admins, remote, prestataires), pas juste un % global.

Segmentation recommandée

  • Admins (PAM), accès consoles, accès cloud.
  • Accès remote (VPN, bastion, VDI).
  • Prestataires et comptes temporaires.
  • Applications métier critiques (SSO).

Pièges

  • MFA uniquement sur “une partie” (admins oui, mais pas les accès sensibles SaaS).
  • MFA faible et facilement phishable sans protections complémentaires.
  • Exceptions permanentes (comptes legacy).

Dossier : Lecture du Dashboard (tendances)

Ce qu’on veut lire dans une courbe

  • Stock : combien de vuln ouvertes (par criticité).
  • Flux : combien arrivent (découvertes) vs combien sortent (fermées).
  • Saisonnalité : releases, audits, campagnes de scan.
  • Signal : si le stock monte, soit on découvre plus, soit on corrige moins (ou les deux).
Lecture rapide : si les découvertes augmentent mais les fermetures n’augmentent pas, le backlog gonfle. Solution : augmenter la capacité de fix, réduire le bruit, ou traiter par lots (legacy, dépendances).

Dossier : Cadre de décision mensuel

Pourquoi ce bloc existe

Le dashboard doit conduire à une liste courte d’arbitrages. Un bon comité mensuel ne discute pas “de la sécurité”, il tranche des décisions concrètes : budget, priorités, acceptations, refontes.

Format recommandé (30 minutes)

  • Top 3 risques (scénario + impact + probabilité) et décision attendue.
  • KPIs : écarts vs objectifs (MTTR, critiques, exceptions expirées, MFA admins).
  • Plan d’action : owners, dates, mesures compensatoires, revalidation.

Arbitrage : App_Legacy (Refonte vs Risque)

Question à trancher

Est-ce qu’on finance une refonte (ou un gros chantier de réduction de dette) ou est-ce qu’on compense le risque avec des contrôles autour (segmentation, WAF, restriction d’accès, monitoring) ?

Options typiques

  • Refonte : baisse durable du risque, coût et délai élevés.
  • Hardening : patching, config, réduction surface, coût moyen.
  • Compensation : isoler et surveiller, coût rapide, risque résiduel non nul.
  • Décommission : supprimer le produit si possible, meilleur ROI.
Décision attendue : owner, budget, trajectoire (3 mois / 6 mois), et une mesure compensatoire immédiate si le risque est haut.

Décision : Validation Budget EDR

Pourquoi c’est un arbitrage

L’EDR est une brique de détection/réponse. Le débat utile n’est pas “on en veut”, mais : couverture, opérations, intégration SOC, et capacité de containment.

Points à valider avant achat

  • Périmètre : serveurs critiques, postes admins, environnements sensibles.
  • Opérationnel : qui répond aux alertes, 24/7 ou non, playbooks.
  • Mesures : MTTD/MTTR attendus, réduction du dwell time.
  • Intégrations : SIEM, ticketing, IAM, isolation réseau.

Décision : Extension dérogation Prestataire_X

Question à trancher

Prolonger une exception doit être une exception elle-même. On revalide le scénario, l’impact, les compensations et la date de fin.

Checklist de revalidation

  • Pourquoi le plan de sortie n’a pas été tenu ? (dépendance, budget, oubli)
  • Compensations toujours en place ? (MFA, segmentation, monitoring)
  • Risques nouveaux ? (accès élargis, nouvelles données, nouvel environnement)
  • Nouvelle date de fin + owner + jalons intermédiaires.
Si l’exception est expirée, la première action est de la requalifier immédiatement, pas de la “laisser traîner”.

Feuille de Route

Une roadmap sécurité n’est pas une liste de courses. C’est une trajectoire : réduire le risque rapidement (30j), structurer pour tenir dans le temps (60j), et devenir résilient (90j). Cliquez sur une fenêtre pour ouvrir le dossier complet : objectifs, dépendances, livrables, owners, et critères de succès.

Une roadmap efficace a des critères de succès (mesurables), des dépendances explicites, et une gestion des exceptions. Sinon, elle se transforme en backlog infini.

Cadre : Comment piloter une roadmap sécurité

Règles simples qui évitent l’échec

  • 1 owner par chantier + un sponsor métier si impact opérationnel.
  • Un livrable = une preuve (re-test, rapport, logs, captures, config).
  • Des critères de succès : KPI + seuil + délai.
  • Dépendances visibles : IAM/logging/CI/CD (Continuous Integration / Continuous Deployment) avant certains chantiers.
  • Fenêtres : 30j = quick wins, 60j = process, 90j = résilience.
Question de pilotage : “Qu’est-ce qui baisse le risque le plus vite, sans créer de dette supplémentaire ?”

30 jours : Urgence (réduction immédiate)

Objectif

Couper les chemins les plus courts vers l’impact : vuln critiques, comptes admins exposés, accès distants faibles. On vise un effet “stop the bleeding”.

Chantiers (détaillés)

  • Fix critiques pentest : patch + configuration + re-test + preuve.
  • Comptes admins : inventaire, suppression orphelins, MFA renforcé, PAM si possible.
  • Accès distants : MFA obligatoire, restrictions IP/geo, durcissement bastion.
  • Réduction surface : endpoints test, interfaces oubliées, debug, pages d’admin publiques.
  • Mitigations rapides : WAF/rate-limit sur auth/export si risque élevé.

Livrables & preuves attendues

  • Rapport “clean-up” : ce qui a été corrigé, où, quand, par qui.
  • Re-tests : captures / scans montrant la fermeture.
  • État IAM : comptes admins listés + MFA + exceptions justifiées.

Critères de succès

  • 0 critique exploitable sur prod sans compensation.
  • MFA sur accès remote + admins.
  • Backlog critique sous contrôle (tendance décroissante).

60 jours : Structuration (process & système)

Objectif

Passer du “one-shot” à la machine : inventaire, ownership, CI/CD (Continuous Integration / Continuous Deployment) gates, SLA, exceptions. On construit le mécanisme qui empêche le retour en arrière.

Chantiers (détaillés)

  • Inventaire : apps, flux, données, exposition, owners, criticité.
  • CI/CD (Continuous Integration / Continuous Deployment) sécurité : SCA (Software Composition Analysis) + secrets scan + gate critique (policy claire).
  • Workflow vuln : intake → triage → assign → fix → verify → prevent.
  • Politique patching : SLA par criticité, exceptions cadrées, reporting.
  • RACI : validé et appliqué (pas juste un slide).

Livrables

  • Matrice RACI signée + process d’escalade.
  • Policy gates CI/CD (Continuous Integration / Continuous Deployment) (ce qui bloque / ce qui alerte).
  • SLA patching + tableau de bord de conformité.
  • Dashboard initial : critiques, MTTR, exceptions, MFA.

Critères de succès

  • Owners renseignés sur les assets critiques (pas de “zone grise”).
  • Gates actifs sur le critique (bloquants) sans explosion de faux positifs.
  • % corrections dans SLA en hausse, MTTR en baisse.

90 jours : Résilience (détecter, contenir, reprendre)

Objectif

Accepter que l’incident arrivera un jour : réduire le dwell time, contenir vite, restaurer proprement, et apprendre. La résilience est un produit, pas un slogan.

Chantiers (détaillés)

  • Exercice de crise : table-top, runbooks, décisions métiers.
  • Détection : logs utiles, alertes actionnables, playbooks SOC.
  • Tiers : revue accès, MFA, clauses incident, revalidation exceptions.
  • Dashboard automatisé : sources de vérité, tendances, alertes gouvernance.
  • Backups/PRA : tests de restauration.

Livrables

  • Compte rendu d’exercice + plan d’action (owners + dates).
  • Playbooks SOC/IR validés.
  • Stratégie annuelle : budget, priorités, jalons trimestriels.

Critères de succès

  • MTTD/MTTR mesurés et en amélioration.
  • 0 exception expirée, revalidation systématique.
  • Capacité de restauration prouvée (tests, délais, preuves).
